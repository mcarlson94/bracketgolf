Build a polished web app called Bracket Golf.

The first and primary focus is to build a Tournament Challenge-style bracket contest for the U.S. Amateur Golf Championship.

The product should look, feel, and work incredibly similarly to ESPN Tournament Challenge, but for the U.S. Amateur match-play bracket.

This is the primary focus.

I care much more about making the bracket experience look and feel incredible than building a bunch of secondary features.

The application should use the real U.S. Amateur field, bracket, and results from the official USGA championship website.

Do not make up player names.

Do not generate fake golfers.

Do not generate fake matchups.

Do not populate the product with fictional U.S. Amateur data.

Use actual tournament data.

---

# PRODUCT VISION

The concept is simple:

ESPN Tournament Challenge, but for the U.S. Amateur.

The U.S. Amateur starts with stroke play and then moves into a 64-player single-elimination match-play bracket.

Once the official 64-player match-play bracket is set, users should be able to fill out the entire bracket by predicting the winner of every match through the championship.

There are:

- 64 golfers
- 63 matches
- 6 rounds

Rounds:

- Round of 64
- Round of 32
- Round of 16
- Quarterfinals
- Semifinals
- Championship

Users select the winner of each matchup.

When a golfer is selected, that golfer automatically advances to the next round.

Users continue making picks until they select their projected U.S. Amateur champion.

The experience should feel extremely familiar to anyone who has ever filled out a March Madness bracket on ESPN Tournament Challenge.

# DETERMINE THE BEST DATA SOURCE

Before building brittle HTML scraping, inspect how the official USGA tournament website loads its data.

Look for:

- Public JSON endpoints
- API requests used by the USGA frontend
- Embedded page JSON
- Structured script data
- GraphQL requests
- REST endpoints
- Tournament feeds
- Structured HTML

Prefer a structured data source whenever possible.

The preferred order is:

1. Existing structured API/feed
2. Embedded structured JSON
3. Structured HTML parsing
4. Server-side scraping as a last resort

Do not build fragile scraping around arbitrary visual CSS selectors if the page is already using a structured endpoint underneath.

Keep the entire integration isolated so it can be replaced later if the USGA changes its site.

# BRACKET PROPAGATION LOGIC

This is extremely important.

Suppose:

Round of 64:

Player A vs Player B

User selects:

Player A

Player A automatically appears in the appropriate Round of 32 matchup.

Then the user selects Player A in the Round of 32.

Then Player A advances to the Round of 16.

Then the user selects Player A again.

Later, the user changes their original Round of 64 selection to Player B.

The application must:

1. Advance Player B to the Round of 32.
2. Remove Player A from that Round of 32 slot.
3. Identify downstream picks involving Player A that are no longer logically possible.
4. Clear those invalid downstream predictions.
5. Require the user to make new picks.

Do not allow impossible bracket combinations.

Bracket dependency logic should be thoroughly tested.

Instead:

Incorrect

Future rounds:

Eliminated

Keep them visible.

This is how a real Tournament Challenge product should behave.

Before lock, invalid future picks caused by the user changing an earlier selection can be cleared.

After lock, historical picks must remain intact.
